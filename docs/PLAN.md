# PracBoard 기획

> 상태: 기획 단계. 이 문서는 서비스 방향이 바뀌면 함께 갱신한다.

## 1. 개요

- **무엇:** 패들렛(Padlet)과 유사한 보드 서비스를 사내용으로 직접 만든다.
- **목적:** 진행하는 교육에서 교육생들이 **실습 결과물을 올리는 용도**.

## 2. 사용 주체와 권한

사용 주체는 4가지다. 관리자를 제외하면 실제로 보는 화면은 크게 다르지 않고, **권한의 범위**가 다르다.

| 주체 | 식별 기준 | 권한 | 범위 |
| --- | --- | --- | --- |
| 관리자 | 이메일 도메인 `teamsparta.co` | Master (전체 CRUD) | 모든 교육 |
| 고객사 담당자 | 해당 고객사의 이메일 도메인 | Read only | 자신에게 read 권한이 있는 교육 |
| 강사 | axhub 배정 | CRUD | 배정된 차시의 보드에 한정 |
| 교육생 | 회원가입 | CRUD | **자신이 회원가입으로 접근한 URL**에 한정 |

### 2.1 인증 (2026-09-29 확정)

사용자 부담을 최소화하려고 **비밀번호를 두지 않는다.** 관리자만 Google로 로그인하고, 나머지는 이메일만 입력한다.

| 주체 | 등록 | 로그인 |
| --- | --- | --- |
| 관리자 | 자동 (`@teamsparta.co`) | **Google 로그인만** |
| 고객사 담당자 | 관리자가 교육에 이메일 등록 (이후 axhub 자동) | 이메일만 입력 |
| 강사 | 관리자가 보드에 이메일 등록 (이후 axhub 자동) | 이메일만 입력 |
| 교육생 | 보드 URL에서 이름 + 이메일 입력 | 이메일만 입력 |

- 비밀번호·메일 인증·초대 링크·비밀번호 재설정이 없다.
- 로그인 화면에서 등록되지 않은 이메일은 거부한다. 교육생 계정은 보드 URL로 참여할 때만 만들어진다.
- `@teamsparta.co` 이메일은 이메일 로그인을 거부하고 Google로 안내한다. 관리자 권한은 DB에서 Google 로그인 여부까지 확인한다(`is_admin()`).
- 로그인 세션은 쿠키로 유지해 자동 로그인되고, 로그아웃 버튼을 둔다.
- 입장 기록(접속 로그)은 남기지 않는다. 카드 작성자·작성 시각으로 충분하다.

**감수한 위험:** 이메일을 아는 사람은 그 사람으로 로그인할 수 있다.
- 교육생: 다른 교육생 이름으로 카드를 올리거나 그 사람의 카드를 지울 수 있다. 보드 자체는 URL만 있으면 참여할 수 있으므로 새로 새는 정보는 없다.
- 고객사 담당자: 담당자 이메일을 아는(추측한) 사람이 그 교육의 결과물 전체를 볼 수 있다. `hr@회사.com` 같은 패턴은 추측하기 쉽다.
- 강사: 강사 이메일을 아는 사람이 그 보드의 섹션·카드를 지울 수 있다.
- 보안이 중요한 서비스가 아니고 이메일 유출 가능성이 낮다고 판단해 감수한다. 특정 고객사가 요구하면 그 교육만 메일 로그인 링크 방식으로 바꾸는 것을 검토한다.

### 2.2 권한 데이터 구조

역할은 사람이 아니라 **연결 관계**에 붙인다. 한 사람이 보드마다 다른 역할을 가질 수 있다.

```
profiles           (id, name, email)                 신원만
education_viewers  (education_id, email, source)     고객사 담당자. source = axhub | manual
board_members      (board_id, email, role)           role = instructor | student
관리자              테이블 없음. Google 로그인 + @teamsparta.co 로 판단
```

- **고객사 담당자:** axhub 교육의 담당자(`courses.client_contact_id` → `client_contacts.email`)를 자동 등록하고, 관리자가 교육 화면에서 추가 등록할 수도 있다. 이메일 기준으로 등록하므로 가입 전에도 권한을 줄 수 있다.
- **강사:** axhub `assignments`(강사 × 차시)를 동기화해 해당 차시의 보드에 권한을 준다. 강사가 바뀌면 **추가만 하고 삭제하지 않는다** (이전·현재 강사 모두 접근). 관리자가 보드 화면에서 직접 추가·해제할 수도 있다.
- **교육생:** 보드 URL로 참여하면 그 보드의 student로 등록된다.
- 권한 시나리오는 `npm run test:rls`(`supabase/tests`)로 확인한다.
- 권한은 화면(`src/lib/permissions.ts`)뿐 아니라 **Supabase RLS**로 DB에서 강제한다. RLS 판단을 단순하게 하려고 `boards`에 `education_id`를 비정규화해 둔다.

## 3. 교육 구조

```
교육
 └─ 회차
     └─ 차시
         └─ (분반)   ← 선택. 필요한 교육에만 추가될 수 있음
```

- 기본 구조는 **교육 → 회차 → 차시**이고, 차시 아래에 **분반**이 추가될 수 있다.
- 구조의 **가장 마지막 단위(최소 단위 교육)** 가 하나의 보드이며, 고유 URL을 가진다.
- 최소 단위 교육은 이후 **axhub와 연동**해서 생성된다.
- axhub 대응: 교육 = `courses`, 회차 = `course_rounds`, 차시 = `course_sessions`.
- 분반은 axhub 데이터를 따른다. 현재 axhub는 분반을 폐지(`class_id` 삭제)했으므로, 연동 시점에는 **차시 하나 = 보드 하나**가 된다.

## 4. 화면 구성

화면은 크게 **관리자 화면**과 **그 외 주체의 화면**으로 나뉜다.

### 4.1 관리자 화면
- 생성된 **모든 교육**을 확인할 수 있다.
- 최상위 카테고리는 **교육**이다. (현재 구현은 기업별로 나뉘어 있음 → 교육별로 변경)
- 교육을 타고 들어가면 회차 → 차시 → (분반) 순으로 최소 단위 교육까지 내려간다.

### 4.2 고객사 담당자 화면
- **하나의 교육 안**에서 확인하는 구조.
- 관리자는 전체 교육을 보지만, 고객사 담당자는 **자신에게 read 권한이 있는 교육만** 볼 수 있다.
- 읽기 전용.

### 4.3 강사 / 교육생 화면
- **주어진 URL(최소 단위 교육)의 보드 하나만** 볼 수 있다.
- 패들렛에서 보드 링크를 받아 들어가는 것과 같은 경험. 다른 교육/차시로 이동하는 탐색은 없다.

## 5. 현재 구현과의 차이

| 항목 | 현재 (mock data) | 변경 방향 |
| --- | --- | --- |
| 최상위 분류 | 기업 (`/enterprises/[enterpriseId]/...`) | 교육 |
| 계층 | 기업 → 교육 → 회차 → 차시 | 교육 → 회차 → 차시 → (분반) |
| 최소 단위 생성 | 화면에서 직접 생성 | axhub 연동으로 생성 |
| 권한 / 인증 | 없음 | 주체별 권한 (2절) |
| 화면 분리 | 단일 화면 | 관리자 / 고객사 담당자 / 강사·교육생 |

보드 내부 구성(섹션, 카드)은 현재 구현을 기반으로 한다.

### 5.1 화면 구현 현황 (2026-09-29)

Supabase 인증·DB로 동작한다 (2.1, 2.2절). 스키마는 `supabase/migrations`, 개발용 초기 데이터는 `scripts/seed-dev.mjs`.

| 경로 | 화면 | 접근 |
| --- | --- | --- |
| `/` | 로그인. 로그인 후 관리자 → `/admin`, 고객사 담당자 → `/client`, 강사·교육생 → 참여한 보드 | 전체 |
| `/admin` → `/educations/[id]` → `/rounds/[id]` → `/lessons/[id]` | 전체 교육 → 회차 → 차시 → 분반 | 관리자 |
| `/client` → (위와 같은 하위 경로) | 내 교육 → 회차 → 차시 → 분반 (읽기 전용) | 고객사 담당자 |
| `/b/[boardId]` | 보드 (최소 단위 교육의 고유 URL) | 권한이 있는 전체 주체 |

- 분반이 없는 차시는 목록에서 바로 보드로 이동하고, 분반이 있으면 분반 목록을 거친다.
- 로그인하지 않은 상태로 보드 URL에 들어오면 회원가입 화면이 나오고, 가입하면 그 보드의 교육생이 된다. 로그인한 사용자가 다른 보드 URL에 들어오면 참여 여부를 묻는다.
- 고객사 담당자는 관리자가 교육 화면에서, 강사는 보드 화면에서 이메일로 등록한다. 등록된 사람은 그 이메일만 입력하면 로그인된다.
- 카드 첨부는 파일 1개(이미지·동영상·오디오·문서 등, **50MB 이하** — Supabase 프로젝트 업로드 한도)다. 비공개 Storage 버킷(`card-images`)에 두고 서명 URL로만 보여주며, 내려받을 때는 원래 파일 이름을 쓴다.
- **실시간 반영:** 카드·섹션이 바뀌면 서버가 보드 채널(`board:<id>`)로 "바뀌었다" 신호만 보내고, 보고 있던 화면이 서버에서 다시 읽는다. 신호에는 내용이 없어서 권한 확인은 항상 RLS를 거친다.
- **수정·삭제 권한:** 카드는 작성자 본인과 관리자·강사, 섹션(추가·이름 변경·삭제)은 관리자·강사, 회차·차시(수정·삭제)는 관리자. 고객사 담당자는 읽기만 한다. axhub에서 받아온 회차·차시를 수정하면 이후 동기화 때 덮어써질 수 있다.
- 강사·교육생 화면에는 상위 경로(브레드크럼)가 없고, 관리자·고객사 담당자는 상위 계층으로 돌아갈 수 있다.
- 권한은 DB의 RLS(`supabase/migrations`)가 강제하고, `src/lib/permissions.ts`는 버튼 표시용이다. 규칙을 바꿀 때 두 곳을 같이 고친다.

**임시로 정한 규칙 (7절 논의 후 확정 필요)**
- 교육생: 카드 작성 가능, **본인이 올린 카드만** 삭제 가능. 섹션 관리는 불가.
- 강사: 배정된 보드의 섹션·카드를 모두 관리할 수 있다.
- 관리자: 회차·차시를 직접 만들 수 있다. (이후 axhub 연동으로 대체 예정)

## 6. 용어

- **교육:** 최상위 단위. 고객사 담당자의 read 권한이 부여되는 단위.
  - axhub의 교육명은 `[기업명] - 교육명` 형태다. 화면에는 교육명만 보여준다. (예: `[삼성전자] - 신입사원 온보딩` → `신입사원 온보딩`)
  - 관리자 화면의 교육 검색은 기업명과 교육명을 함께 대상으로 한다. 고객사별 필터 버튼은 두지 않는다.
- **회차 / 차시 / 분반:** 교육의 하위 단위. 분반은 선택.
- **최소 단위 교육 (보드):** 계층의 마지막 단위. 고유 URL을 가지며 강사·교육생이 접근하는 곳.

## 7. 미정 사항 (이후 구체화)

- **교육생 CRUD 범위:** 보드 전체 게시물인지, 본인이 올린 게시물만인지.
- **axhub 연동 방식:** 동기화 주기(수동 / 주기 실행 / 웹훅), 어떤 계정으로 읽어올지.
- **관리자 화면의 기업 정보:** 최상위가 교육으로 바뀐 뒤 고객사 정보를 어디에 표시할지.
